## 6. Strict Preservation of Operational Business Rules

The following five critical business rules are central to the application's integrity and must be strictly preserved across all current and future refactoring milestones:

### 6.1 Rule 1: SLA Resolution & Exact Declaration Syntax

1. **Resolution Priority**:
   $$\text{Resolved Priority} = \text{explicit } \texttt{priority} \;\;\|\;\; \text{computed } \texttt{computedPriority} \;\;\|\;\; \text{'MEDIUM'}$$
2. **SLA Durations**:
   - `CRITICAL`: 1 hour
   - `HIGH`: 4 hours
   - `MEDIUM`: 24 hours
   - `LOW`: 72 hours
   - Unknown/fallback: 72 hours
3. **Exact Syntax Requirement**:
   `test/unit/sla-resolution.test.js:8-16` uses a regular expression matching the literal syntax:
   ```typescript
   const SLA_HOURS: Record<string, number> = {
     CRITICAL: 1,
     HIGH: 4,
     MEDIUM: 24,
     LOW: 72,
   };
   ```
   *Constraint*: This declaration syntax must remain verbatim to prevent regex parser failure in test suites.
4. **SLA Auto-Escalation**:
   - Cron schedule: `*/15 * * * *` (every 15 minutes).
   - Condition: Ticket status not in `['RESOLVED', 'CLOSED']`, priority not `CRITICAL`, and `slaDeadline <= now + 30 minutes`.
   - Action: Mutates priority to `CRITICAL` and records an `AuditLog` row with `changedBy: 'System (Auto-Escalation)'`.

---

### 6.2 Rule 2: WSJF Prioritization & Form Validation Rules

1. **Formulas**:
   $$\text{Cost of Delay} = \text{BV} + \text{TC} + (\text{R or AW})$$
   $$\text{WSJF} = \frac{\text{Cost of Delay}}{\max(\text{Effort}, 1)}$$
2. **Field Storage**:
   `bv` (Business Value), `r` (Risk Reduction), `tc` (Time Criticality), `aw` (Opportunity Enablement), `effort` (Job Size), `wsjf` (WSJF Score), `impact`, `urgency`, `severity`, `computedPriority`.
3. **Validation Refinements (`src/validation/schemas.ts`)**:
   - Subtype «Доробка» / «modification»: `payload.url` is required.
   - If $\text{TC} \ge 4$: `dueDate` is mandatory (`Кінцевий термін (dueDate) є обов'язковим при Time Criticality (TC) ≥ 4`).
   - Form B with subtype «Вивантаження» / «export»: `payload.exportParams` is required.
   - Form D with subtype «Доступ» / «access»: `payload.role` is required.
   - Form D with subtype «Ліцензія» / «license»: `payload.license` is required.

---

### 6.3 Rule 3: 12-Status Branch Transitions & State Machines

The system defines 12 distinct status values:
`NEW`, `TZ_PREPARATION`, `PENDING_APPROVAL`, `APPROVED`, `TRIAGE`, `ESTIMATION`, `IN_PROGRESS`, `TESTING`, `UAT`, `RESOLVED`, `CLOSED`, `REJECTED`.

1. **Branch A/B/E (Service Requests / ТЗ / Dev Loop)**:
   - `NEW` $\to$ `['TZ_PREPARATION', 'REJECTED']`
   - `TZ_PREPARATION` $\to$ `['ESTIMATION', 'TZ_PREPARATION', 'REJECTED']` *(ТЗ refinement loop)*
   - `ESTIMATION` $\to$ `['IN_PROGRESS', 'TZ_PREPARATION', 'REJECTED']`
   - `IN_PROGRESS` $\to$ `['TESTING', 'TZ_PREPARATION', 'REJECTED']`
   - `TESTING` $\to$ `['UAT', 'IN_PROGRESS']`
   - `UAT` $\to$ `['RESOLVED', 'TZ_PREPARATION', 'IN_PROGRESS']` *(Rework return loop)*
   - `RESOLVED` $\to$ `['CLOSED', 'IN_PROGRESS', 'UAT']`
   - `CLOSED` $\to$ `[]` *(Terminal)*
   - `REJECTED` $\to$ `['TZ_PREPARATION', 'NEW']`
2. **Branch C (Incident Fast-Track)**:
   - `NEW` $\to$ `['TRIAGE', 'IN_PROGRESS', 'REJECTED']`
   - `TRIAGE` $\to$ `['IN_PROGRESS', 'RESOLVED', 'REJECTED']` *(Allows direct resolution for quick fixes)*
   - `IN_PROGRESS` $\to$ `['RESOLVED', 'CLOSED', 'REJECTED']`
   - `RESOLVED` $\to$ `['CLOSED', 'IN_PROGRESS']`
   - `CLOSED` $\to$ `[]`
   - `REJECTED` $\to$ `['NEW', 'TRIAGE']`
3. **Branch D (Approvals / Access / Licenses)**:
   - `NEW` $\to$ `['PENDING_APPROVAL', 'REJECTED']`
   - `PENDING_APPROVAL` $\to$ `['APPROVED', 'REJECTED']`
   - `APPROVED` $\to$ `['IN_PROGRESS', 'RESOLVED']`
   - `IN_PROGRESS` $\to$ `['RESOLVED', 'CLOSED']`
   - `RESOLVED` $\to$ `['CLOSED', 'IN_PROGRESS']`
   - `CLOSED` $\to$ `[]`
   - `REJECTED` $\to$ `['PENDING_APPROVAL', 'NEW']`
4. **Transition Guards**:
   - Transitioning to `RESOLVED` strictly requires a non-empty `resolutionNote`.
   - Idempotent transitions (`current.status === status`) immediately return HTTP 200 without emitting events or mutating the database.
   - Disallowed transitions throw a localized Ukrainian `ValidationError`.
   - Events `application:status_changed` and `statusTransition` emit strictly *after* database commit.

---

### 6.4 Rule 4: ClickUp Fail-Closed HMAC Webhooks & Bidirectional Sync

1. **Fail-Closed Security**:
   - Unconfigured secret $\to$ HTTP 503 (`CLICKUP_WEBHOOK_SECRET is not configured`).
   - Missing signature header $\to$ HTTP 401 (`Missing signature header`).
   - Invalid signature $\to$ HTTP 401 (`Invalid HMAC signature`).
   - Verification uses `crypto.timingSafeEqual` comparing raw body Buffer against incoming signature.
2. **Loop Suppression & Deduplication**:
   - Webhook-initiated updates set `changedBy: 'ClickUp Webhook'` and `actorRole: 'SYSTEM_CLICKUP'`.
   - Outbound sync listener `handleClickUpStatusChange` suppresses sync if initiated by ClickUp.
   - Outbound echo cache (60s TTL) prevents echo loops.
   - Inbound deduplication cache (5s TTL) suppresses duplicate rapid-fire webhooks.
3. **Multilingual Status Mapping**:
   Supports bidirectional translation between Ukrainian (e.g. «на перевірці» $\leftrightarrow$ `UAT`) and English (e.g. `in review` $\leftrightarrow$ `UAT`). Unmapped statuses log gracefully and return HTTP 200 without throwing.

---

### 6.5 Rule 5: Notification Matrix & Storage Integrity

1. **Multi-Channel Notification Matrix**:
   - `NEW`: Requester & POC email, Slack broadcast alert.
   - `TZ_PREPARATION` & `ESTIMATION`: Slack team alert.
   - `PENDING_APPROVAL`: Approvers email, Slack approval alert.
   - `APPROVED`: Requester & Ops email, Slack broadcast alert.
   - `TRIAGE`: Slack critical on-call alert.
   - `IN_PROGRESS`: Requester email, Slack broadcast alert.
   - `TESTING`: Slack QA channel alert.
   - `UAT`: Requester email + Direct Slack DM to requester.
   - `RESOLVED`: Requester email with `resolutionNote` + Direct Slack DM.
   - `REJECTED`: Requester email with `rejectionReason` + Direct Slack DM.
   - `CLOSED`: Requester completion email.
2. **Graceful Degradation**:
   Missing SMTP credentials or Slack tokens no-op cleanly with structured diagnostic logs. Zero unhandled promise rejections (`Promise.allSettled`).
3. **Dual Storage Engine**:
   - Production / Dev: Direct synchronous JSON read/write to `data/local-db.json`.
   - Test (`isTestEnv()`): In-memory database with thread-safe wait locks, preventing test runner concurrency lockups.
